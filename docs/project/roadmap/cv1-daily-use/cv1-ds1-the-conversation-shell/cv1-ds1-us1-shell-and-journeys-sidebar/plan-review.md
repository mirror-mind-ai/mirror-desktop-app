# Plan Review — CV1.DS1.US1

**Date:** 2026-10-21
**Reviewed:** the first version of the plan, the story and the test guide, as authored in the Plan step (uncommitted at review time).
**Outcome:** the plan was revised; the current version is [plan.md](plan.md). The look of the shell was split into [CV1.DS1.TS2](../cv1-ds1-ts2-mirrors-tokens-and-theme/index.md).

## How it was reviewed

Four lenses were chosen for what this plan puts at risk:

- **engineer**, for the stores, the module boundaries, the reducer move and
  test isolation;
- **quality-assurance**, for whether the UI tests prove the acceptance
  scenarios, the moved proof test and the E2E route;
- **experience-designer**, because this is the product's first real screen:
  tokens, typography, the theme, the layout and its states;
- **product-designer**, for whether the cut is right: the meaning of a click
  on a Journey, what a row must show, the empty and failure states, the
  onboarding sequence.

Security and devops were left out: no dependency, no bundle change, nothing
new crossing a boundary.

Each ran as an isolated reviewer (`pi -p` with the persona's full identity,
no tools, no session, nothing logged to Mirror). Each saw the story, the plan,
the test guide, the repository rules, the console being replaced, the current
tokens, the protocol and fake-host excerpts, the existing proof test and the
core's hierarchy rule. A separate synthesis pass deduplicated the findings,
reassigned the ones that drifted to their owning lens, and surfaced the
conflicts and scope changes as decisions. The method is adapted from the
`plan-and-review-parallel` extension, narrowed to four lenses.

## Navigator rulings

The Navigator took the Driver's recommendation on every decision, and the
split: US1 keeps the shell, the sidebar, the stores, lazy open and every
failure state, validated on behavior; the derived palette, type roles, state
and motion tokens, the theme and the launch without a flash become
[CV1.DS1.TS2](../cv1-ds1-ts2-mirrors-tokens-and-theme/index.md), validated
on look.

| Decision | Ruling |
|---|---|
| D1 — what a click on a Journey means | Lazy open: selecting shows the Journey; the session opens on the first send |
| D2 — first run with no usable model | The sidebar is visible and selectable; the sign-in panel takes the conversation area; no session until a model exists; a characterization test of today's gating comes first |
| D3 — drafts on switch | One US3 bullet moves earlier: the draft is kept per Journey in the conversations store |
| D4 — the palette | Both themes derived from one accent hue (the predecessor's mint) and one danger hue, luminance tuned per theme, with a slot table; in TS2 |
| D5 — when the theme is first resolved | Both: applied synchronously before render in `main.tsx`, and a `useTheme` effect with cleanup for the listener; in TS2 |
| D6 — the Journey without a project path | Selectable, not openable: the conversation area carries the reason and the command that sets the path |
| D7 — host unreachable | Two states: host-failed is shell-level, with a "Try again" that re-runs the connection, and nothing to pick; Journeys-failed is sidebar-local |
| D8 — after a failed open | The Journey stays current; the failure is named with the path in the area; sending again retries |
| D9 — a running marker in the sidebar | Shipped in US1, derived from the conversation's running state; "settled while unseen" deferred |
| D10 — live OS-appearance following | In TS2, in both acceptance lists; happy-dom's `change` dispatch checked, a polyfill in `setup.ts` if needed |

## The synthesis, as produced

### 1) SYNTHESIS

The spine is right — Zustand stores, a pure `journeyTree`, the fake host as the only oracle, the console moved rather than broken — but the plan is thinnest exactly where the story's promises live: what a click on a Journey means (today it writes a session and a bound conversation into Mirror on every look, which DS2 must undo), what the stores own versus what stays in components, and how failures before `journeys.list`, during `session.open`, and in background turns are represented and proven. Risk concentrates in four places: the open-on-select gesture; orchestration and the per-Journey conversation entry; tests whose central assertions are vacuous (switching, no-path, host-unreachable) plus theme ambient state under `retry: 0`; and a token set that is two unrelated predecessor families with no state, chrome or alarm vocabulary. To proceed, the Navigator must settle the gesture, first-run, drafts, palette coherence and the no-path/host-failed states; the plan must name store actions, the entry shape, failure targets and the theme lifecycle; and the harness must grow its first two error answers so the test list can carry real oracles.

### 2) DISSENT

◇ engineer

1. The stores are named as state, not actions. `openSession`, `send`, `abort`, the event folding outside `reduceRows` (`session.extension_error` → notice, `agent_settled` → not running, open `diagnostics` → notices) and the bootstrap chain stay in `Conversation.tsx`, `Sidebar.tsx` and the `App` effect, so the invariants the story rests on — open once per Journey, optimistic `running` rolled back when `session.prompt` fails, events folded into the owning transcript — are untested component logic again; and the single `catch` cannot route a connect failure to `host.failed`, a `journeys.list` failure to `journeys.failed`, or a `models.available` failure anywhere. Make them store actions taking the client — `open(client, journey)`, `send(client, journeyId, text)`, `abort(client, journeyId)`, `applyHostEvent(event)` — tested with a stub `{ request }` and scripted event lists; replace the chain with per-step `try/catch` (or `connectToHost()`) naming a target per failure; components call actions and read slices.

2. One `opening` slot beside a map keyed by Journey, with `selected` in a different store, mis-models what the story requires: two concurrent opens share the slot and the first `finally` clears the second's spinner; an entry that exists only after `session.open` resolves cannot carry "opening" or "failed", so the open-once guard reads two fields; `selected ∧ no conversation` is representable and unrendered. One entry per Journey from the first click — `{ status: "opening" } | { status: "open"; session; rows; running } | { status: "failed"; message }` — with `current: journeyId | null` in the same store; the guard is "an entry exists"; say whether a failed open removes the entry or keeps `failed` (Decision 8); pure tests: open twice sends once, concurrent opens keep their own spinners, `current` always points at an entry or null. `journeys.ts` keeps only what the host listed.

3. Routing by `sessionId` is specified for the happy path only. An event whose `sessionId` matches no entry either throws on `undefined.rows`, lands on the current conversation (the leak the switching test guards, on a path it does not exercise), or is dropped; `session.extension_error` carries no session id in the excerpt and the protocol is frozen; `agent_settled` must clear `running` on the owning entry, not the current one. Specify and test beside the moved `reduceRows` test: unmatched → dropped, reason in a comment; `agent_settled` on the owner only; `extension_error` by `sessionId` if the schema carries one, else a store-level notice outside any transcript — state which.

4. `theme.ts` as a module singleton owning `matchMedia`, the root class and `localStorage` has no lifecycle the harness controls: a read at import captures `prefersColorScheme` from first import; a `change` listener attached once is never removed; `reset()` clears neither the `.dark` class on `document.documentElement` nor the key — yet the "fresh render starts dark" test needs storage kept across two renders inside one test while every other theme test needs it empty, and `happyDOM.settings.device.prefersColorScheme` may be left changed. Keep the store to `preference` and `resolved`; put resolution, listener and root class in a `ThemeEffect`/`useTheme` mounted by `Shell` with cleanup removing both (when the first resolution runs is Decision 5); clear `localStorage`, strip `dark`/`light` from `<html>` and restore `prefersColorScheme` per test in `setup.ts` `afterEach`, not per render.

5. "`renderApp()` resets every store" and "`renderApp.tsx` unchanged" cannot both hold, and a hand-maintained reset list plus a `reset` written as `set({ a: initial.a, … })` drifts the first time US2/US3 adds a store or a field — the leak Risks names, reintroduced. Export `resetAllStores()` from `stores/index.ts`, each store registering its `reset` beside its definition; every `reset` is `set(initialState, true)` from one `initialState`; the harness calls only that; one test asserts every module under `stores/` is registered. Correct the plan: `renderApp.tsx` changes.

6. The two palette lists use vocabularies (shell/sidebar vs canvas/surface) matching neither each other nor the existing slots: "muted" in the plan is a text colour while `--color-muted` today is the user-bubble surface, so copying `#9aa8ad` there greys the bubbles; a `--color-sidebar` in `@theme` stays `#0d1011` under `.light` because the light list carries no sidebar value; `card`, `border`, `ring`, `accent-foreground` have no carried value and would be invented under a note claiming provenance. Put a slot table in the plan on the role vocabulary experience-designer defines (Decision 4): every slot populated in both blocks, each value tagged carried (file + theme) or new; map predecessor "muted" to `--color-muted-foreground`, choose a `--color-muted` surface per theme, add `--color-sidebar` and `--color-danger` to both; a test reading `app.css` asserts the `.light` block defines every `--color-*` that `@theme` defines.

7. Nothing says how components subscribe, and the two planned shapes are the two where naive Zustand 5 selectors fail: `useJourneys((s) => journeyTree(s.journeys))` returns a fresh array per call and loops `useSyncExternalStore` (`useShallow` does not help, the nodes are fresh too); a sidebar selecting `s.conversations` re-renders the whole tree on every background `text_delta`. Select stable references and derive with `useMemo`; per-item subscriptions in the tree item (`s.conversations[id]?.status`); `useShallow` for the rare multi-field read; the pane selects `s.conversations[s.current]` only; write the rule in the stores' module comment for US2/US3.

8. `Conversation.tsx` with a component-state draft and a `transcriptRef`, switched by `current`, has no stated React key. Without `key={journeyId}` the instance is reused and Garden's half-typed draft appears in Beds' composer — "the second shows nothing of the first's" violated through the composer, which the switching test does not look at; with the key each pane is its own instance and the draft resets on switch, the only behaviour consistent with "drafts surviving a switch are US3's". Render `<Conversation key={current} />`, say so, and assert Beds' textbox is empty in the switching test (Decision 3).

9. The header "shows the project path" from an unnamed field. `Journey.projectPath` is the catalog's claim; `SessionOpenResult.cwd` is where the host opened; bound to the catalog the header is a readout of the input and cannot disagree with the sidebar even when the host opened elsewhere — and with the fake host answering the same path for both, the test passes either way. The `~` rule is an inline `^\/Users\/[^/]+` regex: macOS-only, matching any first component (`/Users/Shared/x` → `~/x`), unnamed and untested. Bind the header to `session.cwd`, keep `journey.projectPath` for enablement; script one fake-host `session.open` whose `cwd` differs from the listed path and assert the header shows `cwd`; extract `shortenHome(path)` into a named module with a unit test naming its cases, including a non-home `/Users/*` path shown whole (a path the fixture loader accepts, or its allowlist extended deliberately), and a comment that the true home would need the host — a protocol change, outside US1.

10. Names and homes: `stores/transcript.ts` is a pure reducer, not a store; `journeys/journeyTree.ts` is a one-function folder beside `stores/journeys.ts`; the console's `Transcript` renders one row and moves under that name into the story whose successor *is* the transcript; `showProviders`, a panel toggle, sits in the host store; `canUseModels: boolean | null` beside a connection `status` reproduces the console's `client && canUseModels !== null` guard in every "ready" branch. One rule for both concerns — `journeys/{store,tree}.ts`, `conversations/{store,transcript}.ts`, or derivations beside their store — rename `Transcript` → `TranscriptRow` on the move; `showProviders` as `useState` in `Shell`; fold `canUseModels` into `connecting → connected → ready | failed`.

11. The first scripted error answer is a union on `World.journeys`, a one-off though the plan calls it "the first of the error answers": the next are per-Journey `session.open` failures (`journey_has_no_project_path`, `session_open_failed`) and `session_busy` for US3, and quality-assurance needs a connection failure and a held `session.open` now; each as another per-field union is another mechanism, and `World.journeys` stops meaning "the Journeys". One shape — `failures?: readonly ({ request: "journeys.list"; error } | { request: "session.open"; journey; error })[]` — `World.journeys` stays a list, and `fakeHost.ts`'s header states that an answered error is logged like any answer and an unconsumed one is reported at teardown.

12. `role="tree"`/`treeitem`/`group` with `aria-level` and `aria-current` promises a composite-widget contract — arrow keys, roving tabindex, `aria-selected`/`aria-expanded` — that is out of scope, and `aria-current` is not the tree's selection vocabulary; tests written against those roles must change when the behaviour lands. Decide in the plan: commit to the tree contract now (roving tabindex plus arrow keys, a small testable unit) or use `nav > list > listitem` with `aria-level`, `aria-current`, and `aria-disabled` + `aria-describedby` for the no-path item, so the tests target the right roles once.

◇ quality-assurance

1. "Or the host cannot be reached" has no verification path. Three failures precede `journeys.list` — `hostEndpoint()`, `HostClient.connect` (socket refused, `hello` rejected `unauthorized`/`unsupported_protocol_version`), `models.available` — and the plan never says what the journeys store shows when the host store fails; the fake host grows only a `journeys.list` error, so no test can be written; the Navigator route has no step. The likeliest regression is "Loading Journeys from Mirror…" forever while the reason fades in a toast. State the rule in the plan (whichever Decision 7 picks); add a scripted connection failure to the harness (a `hello` answered with a `HostError`, or an endpoint that refuses); one UI test per failure point, each asserting the message where the Journeys would be and no "Loading"; a Navigator step with the host unable to start, or "host unreachable: not manually verified" recorded as accepted risk.

2. The switching test's central assertion — "Beds showed no Hello and no answer" — is vacuous: `release()` pushes events through the fake socket asynchronously, a `queryByText` null right after passes against a broken router, and nothing accessible shows that Garden's turn finished while Beds is shown, so there is no settling oracle; "Garden shows the whole answer on return" is weakened the same way. Give the test a positive oracle before any negative: the per-Journey running marker product-designer proposes (Decision 9; `aria-busy` / a hidden "working" status the test waits to clear) or `waitFor` on the conversations store's `running` for garden; order it release fully → wait Garden settled while Beds shown → assert Beds' transcript region empty → switch back → assert the whole answer.

3. Outbound routing is untested: with one conversation per Journey, Stop/Send and the `sessionId` on `session.prompt`/`session.abort` must follow the current Journey, and a stale closure or a global `busy` passes every listed test — Stop in Beds aborting Garden, or Beds locked while Garden answers. Extend the switching test: while Garden's turn is held and Beds shown, Beds offers Send not Stop; a prompt sent in Beds (second scripted turn) carries `session-2`; back in Garden before release, Stop is shown and `session.abort` carries `session-1`. This is routing, inside US1, not Stop's effect.

4. The `session.open` failure path and open-time concurrency are untested and the harness cannot express them: `session_open_failed`/`journey_not_found` leave spinner, `aria-current` and the current conversation unspecified, and the plan does not say whether a retry pick is allowed under "exactly one"; "exactly one" is exercised by one click, while a double click or a click on Beds while Garden opens (real opens take seconds) lets a late Garden result steal the view. Add a scripted `session.open` error and assert the spinner clears, the item's `aria-current` per Decision 8, the error named, and a second pick sends a second `session.open`; `await user.dblClick(item)` in the "exactly one" test; a held `session.open` answer mirroring held turns, testing pick Garden → pick Beds → release Garden → Beds stays current — or that interleaving in the Navigator route explicitly.

5. The no-project-path test's "no `session.open` was sent" is trivially true without a click; a `treeitem` is not a `<button>`, `disabled` does not block clicks on it and `aria-disabled` is advisory, so only an attempted click proves the handler refuses. A pathless parent whose active child has a path is realistic and uncovered; a disabling wrapper around the parent can block or hide the child. `await user.click(item)` then assert zero `session.open`, `aria-disabled="true"` and the description text; add a world with a pathless parent over a pathed child, asserting the child is enabled, at `aria-level` 2, and opens exactly once.

6. The hierarchy world (Garden, Beds, Attic, Loft) has one child per parent and roots already alphabetical in listing order, so an insertion-order tree passes; case-insensitivity, depth ≥ 3 and malformed `parent` links are untested, and a self-parent or two-node cycle sends a naive recursion into a loop that blanks the sidebar. The Navigator's oracle is "as `mirror journeys` groups them" while the UI reimplements the sort; a code-point compare and the core's collation disagree on accented names. Unit tests for `journeyTree`: a reverse-alphabetical fixture with mixed case and an accented name against the core's order (pin the collation in the plan — `localeCompare` with the core's options — or state UI order is its own and amend the Navigator oracle); a grandchild at level 3; self-parent and cycle terminating with both at root; all-inactive and zero Journeys → "No active Journeys", plus one UI test for that empty state.

7. The determinism step runs one shuffle seed — one ordering; the theme's ambient state (engineer 4) surfaces only when the theme test runs first, and under `retry: 0` that is an intermittent red gate. Run three or more seeds; extend the "renders twice" test to assert empty storage and no root class, not only store fields.

8. Theme acceptance disagrees between plan and route: Navigator step 5 requires "with system chosen, toggling the OS appearance switches the app", which no acceptance line or UI test promises, and the Risks note concedes happy-dom may not emit `change`. Untested: choosing `system` after `dark` (re-follows the OS; what is stored), an unknown stored value (fallback to `system`, no throw, a class still applied), and class exclusivity (both `dark` and `light` on `<html>`). Decide live following (Decision 10) and say it in both lists; if yes, verify happy-dom dispatches `change` on the flip, else name the polyfill in `setup.ts`; add the three edge-case tests and assert exactly one class in every theme test.

9. "Remembered across launches" is proven only under `npm run dev`, whose origin is the Vite server; the bundle's is `tauri://localhost`, `localStorage` is per origin, WebKit custom-scheme storage has its own behaviour, and the gate builds but never launches the built app. Add a relaunch check on the built bundle to the Navigator route and record the origin exercised in Validation Evidence; until then, persistence in the bundle is a known risk.

10. The console's second test — ending mid-turn without the remainder reaching the next test — is not named among the moving tests, and `vitest list --filesOnly` cannot see a test dropped inside a renamed file; it is the suite's standing turn-leakage guard, needed more with two sessions per test. Name it in the plan's list and the guide's expected list; compare test names (`vitest list` without `--filesOnly`) and expect it under the shell's file.

11. The Navigator route contradicts the stop condition: step 3 opens "another Journey with a project path" the Navigator has not named, binding a conversation to it; step 4 clears a path with `set-path <slug> ""` and says "restore after" without capturing the original; step 3 is also the first time two embedded Pi sessions with Mirror's logger run at once against one `memory.db`, and the route observes only the UI. Require two named Journeys (or a named scratch one) in the header and the stop condition (or revisit under Decision 1); record `mirror journeys` output in Validation Evidence before step 4 and restore from it; after step 3, observe with the CLI that the prompt and answer are logged under `<journey>` only and the second Journey holds an empty new conversation.

12. No-model gating moves without a characterization test: every App test scripts `models: [model]`; today `models: []` forces the sign-in panel and no Journey can be picked; in the shell the sidebar is always visible and nothing pins whether a Journey can be opened with no model (header "model?", Send enabled until `session.prompt` fails). Write the characterization test before the move, then assert whichever rule Decision 2 picks — a click sends no `session.open` until a model exists, or it does and the header states the absence — in the acceptance list.

◇ experience-designer

1. The two palettes are two unrelated predecessor families presented as one product in two lights: dark has a mint accent `#85dfd2`, orange danger `#ff7043` and a sidebar/shell split (`#0d1011` on `#0b0d0e`) below the threshold of sight; light is Tailwind blue-600 `#2563eb`, gray-800 text, crimson danger and a visibly tinted canvas/surface split; neither proposes accent-foreground, hairline, raised surface, selection or ring; muted text sits at ≈7.8:1 in dark and ≈4.5:1 in light, calm in one and faint in the other. With `system` the default, hue — the only identity in an imageless interface — changes family every sunset; light reads as the unstyled starter the roadmap row forbids; `daylight` was one of eight siblings, not dark's counterpart, so pairing them is the pattern-library use the rules warn against. Choose one accent hue and one danger hue as product constants and derive both themes (same hue, luminance tuned per theme to ≥4.5:1 as text and ≥3:1 as fill, accent-foreground derived with it); define one role vocabulary — canvas, sidebar, raised surface, text, muted text, hairline, selection, accent, accent-foreground, ring, danger, notice — used by both sets, with the sidebar in the same relationship to the canvas in both; carry predecessor values only where they survive the derivation, the note saying what changed and why; record the hue constants in D11 (Decision 4).

2. Decision 1 puts typography to the Navigator as a dependency question, not a feeling: the system stack is right for an instrument (Finder, Notes, Terminal) and the website's display face would make the window a landing page — that is the choice. `--font-display` equals `--font-sans`, so the display role is empty; "14 px base as the predecessor used" cannot serve a 13px-density tree, a header carrying a name and three mono facts, and long reading at once; and no measure is set, so a transcript runs the full width of a 1400px window. State the intent — native, quiet, legible at density — and recommend the system stack on it; define roles: sidebar row 13/18 with the current row one weight heavier, header name 14 semibold with path, model and thinking in 12 mono muted with tabular numerals right-aligned or on a second line, transcript body 14–15/22 (US2 inherits), meta 11–12; collapse `--font-display` into sans or give it deliberate weight and tracking; set the conversation's measure (≈70ch, centred) in `Conversation.tsx`; align the header text to the traffic lights' optical centre.

3. The open is undesigned. `@theme` defaults are the dark values and the root class arrives after first render, so a system-light user gets a dark frame every launch over a white pre-paint; the sidebar and footer then rewrite connecting → identity → loading → listed against a host that answers in tens of milliseconds; and `EmptyConversation.tsx`, the screen every launch lands on until DS2 adds resume, is one line — it will become the console's "Open a Journey" heading with a stock icon. The theme test passes whether `.light` lands at frame 0 or 2, and the route does not point the Navigator's eye at it. Resolve preference and `matchMedia` and apply the root class and `color-scheme` synchronously before `render` in `main.tsx` (Decision 5); set the window background to the shell token so the pre-paint matches; show loading affordances only past ≈200ms and let the footer settle once; specify the empty conversation as canvas plus one centred muted line in the product's voice, no icon, no button; add "no flash on launch in either appearance" to the Navigator's theme step.

4. Six colours per theme, and no treatment for the states the shell is made of: current, hover, keyboard focus, the disabled no-path row, the row being opened, the composer's raised surface, hairlines, radius, and the motion for "opening" and "streaming". Each moved component keeps the console's one-column idioms — `hover:border-accent` on `rounded-xl` cards, `disabled:opacity-50`, `rounded-2xl` bubbles, a full-saturation `animate-spin` and an `animate-pulse` accent dot: 12–16px radii and accent outlines say consumer chat, two motion idioms say two products, and the current-Journey mark becomes whatever the first component styles. Add to the Tokens item: `--color-selection` (a low-saturation fill, not the accent), `--color-hover`, a disabled text level on muted (never opacity), hairline as the only border, radius capped at 6px for rows and controls, and one motion rule — a single slow muted indicator shared by opening in the tree and streaming in the transcript; the current row filled with the name one weight heavier; the ring on keyboard focus only.

5. What a tree row shows is undefined, and the no-path reason as an "accessible description" is satisfied by a `title` or a hidden span while the console's idiom — `opacity-50`, `cursor-not-allowed`, the reason in a delayed tooltip — is the obvious carry-over; three-line cards nested three deep in a 240px sidebar become a stacked wall, and a half-transparent row with no visible reason has the posture of a broken control. A row is one line of the name (≈28–30px, 12–16px indent per level); the path lives in the header; the no-path row keeps full-contrast muted text and a visible second line in the same register — "No project path yet" — which is also its description; the opening indicator takes the leading glyph slot so the row does not reflow; the selection fill marks the current row.

6. Picking a Journey fires the app's slowest request and the only feedback is a spinner on the row, while the conversation area — where the eye is — stays on the previous Journey or the empty state until the result; name and path are known before the open starts, so withholding them makes a one-second wait feel like a missed click and invites a second (the guard prevents the double open; the doubt is already felt), and that first-open wait sets the rhythm instant switches are measured against. Mark the row current at once and switch the area immediately, the header's name and `~`-path from the Journey with model and thinking as empty slots until the result, one quiet muted line ("Opening in ~/garden…") that disappears on success; add to the acceptance that the header shows name and path before the open resolves (the state set is product-designer's 5; under Decision 1 this feedback moves to the first send).

7. The failed sidebar state is "the host's error message, by name", the acceptance locks that raw string in as the oracle, and the connect effect still toasts it — so a Mirror that is not configured opens with a log line in the sidebar and a toast sliding over the conversation area in the same instant: the machine talking past the person, twice, as the first words of a fresh install. Structure the inline state: a heading in the product's voice per `HostError.code` ("Mirror isn't set up on this Mac yet"; "The host didn't answer"), the host's message beneath as muted mono detail, no alarm icon, the oracle on the detail line only; never toast a standing state; toasts are for actions that failed, styled on the tokens so sonner's skin is not a foreign object, and positioned clear of the composer at bottom-right.

8. One `--color-danger` with "the amber notices and red error text" both moved onto it collapses two tiers of alarm into one: a retry, an extension that failed on an event, a resource that did not load are notes; a turn that ended in error is a failure; and the open result's `diagnostics` render as one coloured line each at the top of every fresh conversation, so a Journey with one slow extension greets the person in a tone of fault every time. Make the scale explicit: muted for informational diagnostics, `--color-notice` (desaturated warm) for retries and extension notices, `--color-danger` for failures only, the same hue families in both themes; render open diagnostics at the muted level — US2 may collapse them, their tone is decided here.

9. The plan removes session and conversation ids from the header as diagnostics, then keeps a permanent `node · pi · mirror` line in the sidebar footer beside "Providers" and the theme control, and says nothing about the Sparkles mark or the Compass glyph: permanent chrome is the product's self-description, a versions readout narrates machinery the way a dev console does, "Providers" is vendor vocabulary, Sparkles the generic AI glyph and Compass a travel glyph — the spike's placeholders. Move the versions behind an about/diagnostics affordance or the app menu (if they stay for the Navigator's run, say so in the plan and date their removal); keep the footer to what the person acts on — a quiet icon button labelled "Sign in", a quiet icon control for appearance rather than a labelled segmented control; drop Sparkles; if a glyph leads rows, one monochrome muted mark that is neither stock-AI nor travel, or none.

◇ product-designer

1. Selecting a Journey is the same gesture as starting a conversation: a click runs `session.open`, which spawns Pi in the project path and binds a new Mirror conversation, with no moment of intent and nothing in the shell that says it happened. The job is "move between Journeys the way I move between projects" — a look, not an act — yet a person who clicks through five Journeys leaves five sessions and five empty bound conversations on every launch; the plan treats the write as consequential for the Navigator ("a Journey they name, and nowhere else") but gives the person no restraint; and DS2's "list, resume, new" cannot keep select meaning "open a new session", so US1's central gesture, acceptance line and tests are built to be undone. Split look from act: selecting shows the Journey (header with name and `~`-path from the record, the empty transcript, the composer); the session opens on the first send, and in DS2 on an explicit New/Resume; model and thinking join the header once the session exists; "exactly one session per Journey, opened once across switches" stays as acceptance, anchored to the first send. If open-on-select is kept, the header must at least state that a conversation was started and bound (Decision 1).

2. A turn running in a Journey the person is not looking at has no surface: the tree item spins only while opening, so an idle Journey and one whose agent is running tools in `~/garden` on the person's behalf look identical; they cannot tell it finished or which of several is still running — "never wonder where it runs" fails on whether it is running at all. Derive a running indicator on the tree item from the conversation's `running` (no new state) with an accessible status such as "working"; add one flag per conversation, cleared on select, for "settled while unseen", shown as a quiet marker (defer that to US2 if the Navigator prefers; the running indicator ships in US1 and doubles as quality-assurance's settling oracle); Stop from the sidebar stays DS2's, acceptable only because the indicator tells the person where to go (Decision 9).

3. Every empty and failure state names the condition and none names the next step: "No project path yet" hangs off the one control the person cannot operate, with no room for the remedy the test guide itself uses (`mirror journey set-path`); "No active Journeys" hides whether there are paused ones to reactivate; the sidebar's failure is written for the engineer when the fix happens outside the app; the empty conversation invites a pick whether or not there is one. Add a microcopy requirements list to the plan (wording to the writer): no-project-path → the reason plus the command that sets it, visible in the item and, when selected, in the conversation area (prefer selectable-but-not-openable so the explanation has room; the index's "disabled" becomes "cannot start a conversation" — Decision 6); no active Journeys → how to create or reactivate one, with the count of inactive ones; the failed sidebar → "Try again", since the fix happens outside the app (its voice and structure are experience-designer's 7); empty conversation → "pick a Journey" only when there is one to pick.

4. "Host cannot be reached" and "Mirror is not configured" get the same treatment though one disables the Journeys list and the other the whole app: with no host there are no models, no providers panel, no session, no composer that can send; the shell would show a message in the sidebar, an empty area inviting a pick, and a footer whose only working control is the theme — no way back short of quitting, at launch, when this is most likely. Two distinct states: journeys-failed → sidebar-local message with its next step, the area's empty state as designed; host-failed → shell-level, the area carries the plain statement and a "Try again" that re-runs the connection, the sidebar shows nothing to pick and no invitation; automatic reconnection and quit/restart stay DS2's (Decision 7).

5. The conversation area defines two states — nothing picked, open — and leaves opening and open-failed undefined; a failed `session.open` (a path gone from disk, `mirror mirror load` failing) is a toast that fades, as in the console, while the sidebar may still mark the Journey current beside an area that says "pick a Journey" or is blank: the person cannot tell whether Garden is open, broken or still opening, has no retry, and the path and failure are gone with the toast. Define the set: empty; opening (header shown, so the person sees where they are going); open-failed (header, the failure named with the path in the area itself, not only a toast, "Try again"); open; the sidebar marks the selected Journey current in all four (Decision 8). With lazy open, opening and failure happen on the first send and render where the answer would.

6. The first-run state — no provider signed in — is "the sign-in panel, as today", but today has no sidebar: either the panel covers the window and the app does not open on a sidebar on first run, or it covers the area while the sidebar is live and picking opens a session with no model, the header falls back to "model?", and Send stays enabled until `session.prompt` fails (why it cannot send is US3's). The onboarding sequence — see your Journeys, sign in, start — is settled by whatever ships first. Specify: the sidebar is visible and selectable from first launch; with no usable model the area shows the sign-in panel in place of transcript and composer (or of the empty state); no session is opened until a model exists (free with lazy open); on sign-in the panel yields to the selected Journey; the header never renders "model?"; the footer button reopens the panel, dismissible (Decision 2; quality-assurance's 12 pins it).

7. The one piece of console component state kept out of the stores is the draft — the piece the new primary gesture destroys: type half a prompt, click another Journey to check something, come back, it is gone; keeping it costs one field per conversation in a store US1 already builds, and the gap ships a known loss on the gesture the story introduces, which US3 then fixes. Keep the draft per Journey in the conversations store in US1; Enter/Shift+Enter/Escape and the reasons it cannot send stay US3's; present to the Navigator as moving one US3 bullet earlier so it is decided, not defaulted (Decision 3).

### 3) DECISIONS

1. **What a click on a Journey means.** product-designer 1: select shows; the session opens on first send — the index's "when the person picks it, exactly one session is opened" becomes "when the person first sends", model and thinking appear only after, and the Navigator's switching step no longer binds a second Journey (dissolving quality-assurance 11's stop-condition clash). The plan, engineer 2 (entry from first click), quality-assurance 4 (dblClick, held open) and experience-designer 6 (feedback on pick) assume open-on-select; product's weaker path keeps it and makes the header say a conversation was started. Trade-off: navigation without side effects and no DS2 rework, versus rewriting the index's second and third scenarios, the proof test and the header; stores and tests follow whichever is chosen.

2. **First run with no usable model.** The console: the panel replaces everything, no Journey can be picked. product-designer 6: sidebar visible and selectable from launch, the panel in the conversation area, no session until a model exists, never "model?". quality-assurance 12: characterize today's behaviour first, then pin the chosen rule. Trade-off: "the app opens on a sidebar" holds on first run, versus the console's existing gating; "no session until a model exists" is free under Decision 1 and a new guard without it.

3. **Drafts on switch.** engineer 8: `key={current}` resets the draft per switch — the only behaviour consistent with the plan's non-goal, with an assertion that Beds' textbox is empty. product-designer 7: keep the draft per Journey in the conversations store now, moving one US3 bullet earlier. Trade-off: US3's scope intact and a known loss on the new gesture, versus one store field and an acceptance line US3 would otherwise write.

4. **The palette.** Plan Decision 2 and the Implementation Contract: carry the predecessor's default dark and `daylight` as token sets with provenance. experience-designer 1: derive both themes from one accent and one danger hue, carrying predecessor values only where they survive, hue constants in D11. engineer 6's slot table and `.light` completeness test are required either way. Trade-off: provenance fidelity and no design work in US1, versus one product across appearances (and the "evidence, not a pattern library" rule read the other way); a derived pair means the note documents changes, not copies.

5. **When the theme is first resolved.** engineer 4: resolution, listener and root class in a `ThemeEffect` mounted by `Shell`, read on mount, cleaned up on unmount, so the harness owns the lifecycle. experience-designer 3: resolve and apply the class synchronously before `render` in `main.tsx` so no frame paints in the wrong appearance. An effect runs after first paint — the flash; a pre-render read runs outside `renderApp()`'s reset. Trade-off: test-controlled lifecycle versus a flash-free launch the suite cannot see either way.

6. **The Journey without a project path.** The index, engineer 12 (`aria-disabled` + `aria-describedby`), experience-designer 5 (a non-openable row with a visible second line) and quality-assurance 5 (click it, assert nothing sent): a disabled item. product-designer 3: selectable but not openable, the reason and the `set-path` command in the conversation area, the acceptance "cannot be opened … disabled" becoming "cannot start a conversation". Trade-off: room for the remedy and one consistent "selection shows" model (especially under Decision 1), versus the index as written and a simpler item.

7. **Host unreachable.** The index ("the shell says so by name, where the Journeys would be") and quality-assurance 1 (any pre-`journeys.list` failure puts the sidebar in `failed`; tests assert the message there): one treatment. product-designer 4: two states, host-failed shell-level in the conversation area with a "Try again" that re-runs the connection, the sidebar empty with no invitation. Trade-off: the acceptance line as written and no reconnect action (which edges toward DS2's lifecycle), versus a shell that does not invite what it cannot do. The harness connection failure (quality-assurance 1, engineer 11) is needed under either.

8. **After a failed open.** quality-assurance 4: the item loses `aria-current` and a second pick re-sends `session.open`. product-designer 5: the selected Journey stays current in all four area states, with the failure and "Try again" in the area. engineer 2 needs the plan to say whether the entry is removed or kept `failed`. One rule, then the test.

9. **A running marker in the sidebar.** product-designer 2: ship a derived "working" indicator on the tree item in US1 (defer "settled while unseen" if needed). The plan: a spinner for opening only; quality-assurance 2 can take the indicator as its settling oracle or fall back to `waitFor` on the store; experience-designer 4 would give it the one shared motion. Trade-off: one more sidebar state and its test now, versus a store-read oracle and no visibility of background work until DS2.

10. **Live OS-appearance following.** The test guide's step 5 requires it; no acceptance line or UI test does; the Risks note doubts happy-dom emits `change` (quality-assurance 8). Decide whether it is US1 and write it in both lists, with the polyfill named in `setup.ts` if needed, or strike it from the route.
